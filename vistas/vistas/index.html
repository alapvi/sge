    Las vistas en Odoo 18

    En este capítulo exploraremos cómo funcionan las vistas en Odoo, qué tipos de vistas podemos utilizar y cómo se pueden personalizar mediante XML y acciones de servidor. Aprenderemos a estructurar correctamente una interfaz de usuario, a definir formularios, listados, kanban y gráficos, y a gestionar la navegación entre ellos.

    Las vistas son la manera en la que se representan los modelos. Si no declaramos vistas, se pueden referenciar por su tipo y Odoo generará una vista list o form estándar para poder ver los registros de cada modelo. No obstante, casi siempre queremos personalizar las vistas y en ese caso se suelen referenciar por un identificador.

    Las vistas tienen una prioridad y, si no se especifica el identificador de la que queremos mostrar, se mostrará la que tenga mayor prioridad.

    <record model="ir.ui.view" id="view_id">
    <field name="name">view.name</field>
    <field name="model">object_name</field>
    <field name="priority" eval="16"/>
    <field name="arch" type="xml">
        <!-- contenido de la vista: <form>, <list>, <graph>, ... -->
    </field>
</record>

    Las vistas se guardan en el modelo ir.ui.view. Todos los elementos de interfaz suelen tener en su nombre el prefijo ir.ui (Information Repository, User Interface). Por ejemplo: los menús en ir.ui.menu o las acciones en ir.actions.window.

    Ejemplo de vista form

    <record model="ir.ui.view" id="course_form_view">
    <field name="name">course.form</field>
    <field name="model">openacademy.course</field>
    <field name="arch" type="xml">
        <form string="Course Form">
            <sheet>
                <group>
                    <field name="name"/>
                    <field name="description"/>
                </group>
            </sheet>
        </form>
    </field>
</record>

    Aunque Odoo ya proporciona una vista list y una form por defecto, casi siempre conviene mejorarlas. Todas las vistas tienen field que pueden tener distintos widgets. En las vistas form podemos adaptar mucho el aspecto con grupos de campos, pestañas, campos ocultos condicionalmente, etc.

    Vistas list (Odoo 18)

    En Odoo 18, las vistas tabulares se definen con la etiqueta <list> (los ejemplos antiguos con <tree> se adaptan como <list>).

    Las vistas list son uno de los tipos de vistas más utilizados en Odoo. Permiten mostrar registros en formato de tabla, facilitando la visualización y la gestión de grandes cantidades de datos.

    Son especialmente útiles para representar información resumida de un conjunto de registros, con columnas que muestran los campos más relevantes. Además, pueden incluir funcionalidades como ordenación, filtros y acciones rápidas.

    Ejemplo básico de vista list para res.partner:

    <record id="view_partner_list" model="ir.ui.view">
    <field name="name">res.partner.list</field>
    <field name="model">res.partner</field>
    <field name="arch" type="xml">
        <list>
            <field name="name"/>
            <field name="phone"/>
            <field name="email"/>
            <field name="company_id"/>
        </list>
    </field>
</record>
    • <record>: define un nuevo registro en ir.ui.view, que representa la vista.
    • <field name="name">: nombre único de la vista.
    • <field name="model">: modelo al que pertenece (res.partner).
    • <field name="arch" type="xml">: estructura XML de la vista.
    • <list>: vista tipo lista/tabular.
    • <field .../>: columnas mostradas en la lista.

    Colores (decorations)

    En las vistas list se puede modificar el color según el contenido de un campo con decoration-*, que utiliza colores contextuales de Bootstrap:

    • decoration-bf — líneas en negrita
    • decoration-it — líneas en cursiva
    • decoration-danger — rojo claro
    • decoration-info — azul claro
    • decoration-muted — gris claro
    • decoration-primary — morado claro
    • decoration-success — verde claro
    • decoration-warning — marrón claro
    <list decoration-info="state=='draft'" decoration-danger="state=='trashed'">
    <field name="name"/>
    <field name="state"/>
</list>

    Si se quiere comparar un campo Date o Datetime, se puede usar la variable global de QWeb current_date:

    <list decoration-info="start_date==current_date">
    ...
</list>

    También se pueden aplicar decoration-* a campos individualmente.

    Editable

    Se puede hacer una lista editable para no tener que abrir un formulario:

    • editable="top": crea registros nuevos arriba
    • editable="bottom": crea registros nuevos abajo

    Las listas editables pueden incluir on_write para indicar un método a ejecutar cuando se edita o crea un elemento.

    Campos invisibles

    A veces un campo sirve para lógica interna pero no hace falta mostrarlo. Se puede incluir y marcar como invisible (constante):

    <list decoration-info="duration==0">
    <field name="name"/>
    <field name="course_id"/>
    <field name="duration" invisible="1"/>
    <field name="taken_seats" widget="progressbar"/>
</list>

    Para invisibilidad condicional, en Odoo 18 se recomienda attrs (ver la sección Formularios dinámicos).

    Botones

    Las listas pueden tener botones con los mismos atributos que los botones de los formularios.

    ⚠️ Cuidado con las listas dentro de formularios (x2many): el botón se ejecuta en el modelo de la lista, no en el modelo del formulario que la contiene. Si queremos acceder al padre, hay que usar el atributo parent.

    Totales

    En listas se pueden calcular totales con sum:

    <field name="amount" sum="Total Amount"/>

    Ordenar por un field

    Una lista puede ordenarse por defecto por un campo (no computado) con default_order:

    <list default_order="sequence,name desc">

    Si se quiere que siempre se ordene así, independientemente de la vista, hay que añadir al modelo el atributo _order.

    Agrupar por un field

    Con default_group_by. Como el orden, solo funciona con campos guardados en base de datos.

    <list default_group_by="born_year">
    <field name="name"/>
    <field name="born_year"/>
    <field name="age"/>
</list>

    Vistas form

    Para que un formulario quede bien, se recomienda incluir <sheet>, que evita que el formulario ocupe toda la pantalla en monitores panorámicos.

    Dentro de <sheet> se suelen usar <group> y dentro los field. Se pueden crear tantos group como se quiera, y pueden tener string para mostrar un título.

    Si no usamos group, los campos no tendrán etiqueta (label). Sin embargo, cosas como class="oe_edit_only" no funcionan dentro de group, por lo que a veces hay que usar:

    <label for="name"/>

    Pestañas y separadores

    Pestañas:

    <notebook>
    <page string="Título">
        ...
    </page>
</notebook>

    Separadores:

    <separator string="Description for Quotations"/>

    One2many: modificar la list embebida o la vista usada

    Algunos One2many muestran una vista list por defecto no adecuada. Se puede redefinir la list embebida:

    <field name="subscriptions" colspan="4">
   <list>
      ...
   </list>
</field>

    También se puede especificar la vista form que se abrirá al crear un nuevo elemento (por contexto):

    <field name="m2o_id" context="{'form_view_ref': 'module_name.form_id'}"/>

    Nota: las vistas list embebidas tienen limitaciones respecto a vistas llamadas con un action (por ejemplo, no se pueden agrupar).

    Valores por defecto en un one2many

    Cuando creamos un One2many en modo form (o list editable), podemos crear elementos de la relación. Para que al crearlos el Many2one apunte al padre, se usa contexto:

    context="{'default_<campo_many2one>': active_id}"

    Ejemplo dentro de un action:

    <field name="context">{"default_doctor": True}</field>

    active_id apunta al id del elemento activo (en un formulario, el registro actual). En creación puede no existir aún en BD, pero internamente funciona.

    Domains en Many2one y Many2many

    Los Many2one se pueden filtrar con domain:

    <field name="hotel" domain="[('ishotel', '=', True)]"/>

    Funciona igual para Many2many.

    Widgets

    Algunos campos se pueden mostrar con un widget distinto al por defecto:

    <field name="image" widget="image" class="oe_left oe_avatar"/>
<field name="taken_seats" widget="progressbar"/>
<field name="country_id" widget="selection"/>
<field name="state" widget="statusbar"/>

    Las vistas form, list o kanban muestran campos en widgets. Cada field tiene un widget por defecto, pero puede cambiarse.

    Integer y Float

    • widget="integer": muestra el número sin separadores; si no hay valor, muestra 0.
    • widget="char": muestra el número; si no hay valor queda vacío y el campo suele ser más ancho.
    • widget="id": muestra el número pero no se puede editar.
    • widget="float": muestra el número con decimales.
    • widget="percentpie": gráfico circular con porcentaje (no funciona en list ni en kanban).
    • widget="float_time": muestra el float como tiempo.
    • widget="progressbar": barra de progreso (funciona en list y form, no en kanban).
    • widget="monetary": muestra el número con 2 decimales.
    • widget="gauge": gráfico semicircular (solo en kanban).

    Ejemplo de gauge con opciones:

    <field name="current"
       widget="gauge"
       options="{'max_field': 'target_goal', 'label_field': 'definition_suffix', 'style': 'width:160px; height: 120px;'}"/>

    Char y Text

    • widget="char": editor de una línea.
    • widget="text": campo más alto para varias líneas.
    • widget="email": crea el enlace para enviar un correo.
    • widget="url": crea un enlace con http.
    • widget="date": permite guardar fechas como cadenas.
    • widget="html": editor WYSIWYG (texto con formato).

    dashboard_graph

    Muestra un gráfico pequeño indicando una progresión. Necesita guardar (o generar) en un char un JSON concreto, por ejemplo:

    [{"values":
        [{"label":"2019-01-31","value":"7"},
         {"label":"2019-02-01","value":"20"},
         {"label":"2019-02-02","value":"45"},
         {"label":"2019-02-03","value":"34"},
         {"label":"2019-02-04","value":"40"},
         {"label":"2019-02-05","value":"67"},
         {"label":"2019-02-06","value":"80"}],
 "area":true, "title":"Next Week", "key":"Occupation", "color":"#7c7bad"}]

    Ejemplo XML:

    <field name="week_ocupation" widget="dashboard_graph" graph_type="bar"/>

    En ejemplos reales suele ser un campo computed que genera el JSON con json.dumps():

    values = []
for i in record.sales:
    reserves = i.quantity
    values.append({'label': str(i.name), 'value': str(reserves)})
graph = [{'values': values, 'area': True, 'title': 'Sales', 'key': 'Sales', 'color': '#7c7bad'}]
h.graph_data = json.dumps(graph)

    Opciones: - type: bar o line. En line, en lugar de label y value, se usan x e y.

    Boolean

    Ribbon (Odoo 13): muestra una cinta en el formulario para un boolean importante:

    <widget name="web_ribbon" text="Archived" bg_color="bg-danger"/>
<widget name="web_ribbon" text="Paid"/>

    boolean_toggle (en list): permite activar un boolean en la tabla.

    Date

    daterange: muestra un rango de fechas.

    date_begin = fields.Datetime(string='Start Date')

    <field name="date_begin" widget="daterange"/>

    Many2one

    • widget="many2one" (por defecto): selector con opción de crear. Se pueden desactivar opciones:
    <field name="field_name" options="{'no_create': True, 'no_open': True}"/>
    • widget="many2onebutton": botón que indica si está asignado; al pulsar abre el formulario.

    Many2many

    • widget="many2many": lista con opción de borrar/añadir.
    • widget="many2many_tags": etiquetas.
    • widget="many2many_checkboxes": lista de checkboxes.
    • widget="many2many_kanban": muestra un kanban asociado (requiere vista kanban definida).
    • widget="x2many_counter": solo muestra la cantidad.

    many2many_tags_avatar:

    partner_ids = fields.Many2many('res.partner', 'calendar_event_res_partner_rel', string='Attendees')

    <field name="partner_ids"
       widget="many2many_tags_avatar"
       write_model="calendar.contacts"
       write_field="partner_id"
       avatar_field="image_128"/>

    One2many

    • widget="one2many": por defecto.
    • widget="one2many_list": se mantiene por retrocompatibilidad.

    Modificar la list del One2many (Odoo 18)

    Antes se hacía con <tree>. En Odoo 18 se usa <list>:

    <field name="fortress">
   <list>
     <field name="name"/>
     <field name="level"/>
   </list>
</field>

    Formularios dinámicos en Odoo 18 — sin attrs

    En Odoo 18 ya no se usa attrs en las vistas XML.
    En su lugar, las condiciones se escriben directamente en los atributos:

    • invisible="..."
    • readonly="..."
    • required="..."

    Las expresiones usan sintaxis similar a Python (==, !=, and, or, not, etc.).

    Ejemplo de patrón típico (equivalente al que antes se hacía con attrs):

    <field name="some_field"
       invisible="is_done == True"/>

    Ocultar condicionalmente

    Antes (con attrs):

    <field name="boyfriend_name"
       attrs="{'invisible': [('married', '!=', False)]}"/>

    Ahora (Odoo 18):

    <field name="boyfriend_name"
       invisible="married != False"/>

    Si married es un booleano y quieres ocultar el campo cuando está casado:

    <field name="boyfriend_name"
       invisible="married"/>

    Readonly condicional

    Antes:

    <field name="name2"
       attrs="{'readonly': [('condition', '=', False)]}"/>

    Ahora:

    <field name="name2"
       readonly="condition == False"/>

    Otro ejemplo típico:

    <field name="amount"
       readonly="state != 'draft'"/>

    Combinar varias reglas

    Antes (varias reglas dentro de attrs):

    <field name="name"
       attrs="{
           'invisible': [('condition1', '=', False)],
           'required':  [('condition2', '=', True)],
           'readonly':  [('condition3', '=', True)]
       }"/>

    Ahora (cada atributo con su propia condición):

    <field name="name"
       invisible="condition1 == False"
       required="condition2 == True"
       readonly="condition3 == True"/>

    Puedes usar expresiones más complejas, por ejemplo:

    <field name="budget"
       readonly="completion_rate == 100 or state == 'cancel'"/>

<field name="deadline"
       required="priority == 'high' and not completed"/>

    Guía rápida:

    • Usa invisible="expresión" para mostrar/ocultar campos según otros campos.
    • Usa readonly="expresión" para bloquear edición en ciertos estados.
    • Usa required="expresión" para hacer obligatorios campos en determinadas condiciones.
