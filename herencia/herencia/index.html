    Herencia — Modelos, Vistas y Controladores

    Guía docente para desarrollo en Odoo 18, con ejemplos concretos basados en el módulo task_app y esquemas visuales para ayudar a tu alumnado a entender la herencia.

    Objetivo del documento

    En este documento verás:

    • Los tipos de herencia en Odoo 18 (_inherit, _inherits).
    • Cómo aplicar herencia en:
    • Modelos
    • Vistas
    • Controladores (métodos Python)
    • Ejemplos concretos basados en task_app.task_model.
    • Esquemas visuales de clases y relaciones.

    Concepto general de herencia en Odoo

    La herencia permite extender y adaptar módulos existentes sin tocar su código original, evitando problemas en futuras actualizaciones.

    Se puede aplicar en las tres capas del patrón MVC:

    Capa Qué se hereda o extiende Ejemplo
    Modelo Campos, constraints, métodos ORM Añadir campos a task_app.task_model
    Vista Campos visibles, disposición, etiquetas, botones Añadir pestaña nueva al formulario de Task
    Controlador Lógica de negocio (métodos create, write, action_*) Añadir validación extra en create()

    Odoo soporta tres grandes mecanismos de herencia de modelos:

    1. Herencia de clase → _inherit + mismo _name
    2. Herencia por prototipo → _inherit + _name distinto
    3. Herencia por delegación → _inherits

    Herencia en MODELOS con task_app

    Partimos de un modelo base sencillo:

    # task_app/models/task_model.py
from odoo import fields, models

class TaskModel(models.Model):
    _name = "task_app.task_model"
    _description = "Task"

    name = fields.Char(string="Name", required=True, index=True)
    description = fields.Text(string="Description")
    is_done = fields.Boolean(string="Done", default=False)

    Herencia de clase sobre task_app.task_model

    Caso típico: queremos añadir campos y métodos sin cambiar el modelo original.

    Ejemplo: añadir fecha límite y prioridad a las tareas

    # task_app_extension/models/task_inherit.py
from odoo import api, fields, models
from odoo.exceptions import ValidationError

class TaskModel(models.Model):
    _inherit = "task_app.task_model"     # mismo modelo, no definimos _name

    deadline = fields.Date(string="Deadline")
    priority = fields.Selection(
        [('0', 'Low'), ('1', 'Normal'), ('2', 'High')],
        string="Priority",
        default='1',
        index=True,
    )

    @api.constrains("deadline")
    def _check_deadline(self):
        for task in self:
            if task.deadline and task.deadline < fields.Date.today():
                raise ValidationError("Deadline cannot be in the past.")

    Visual — Diagrama de clases (herencia de clase)

    classDiagram
    class TaskModel_Base {
      +Char name
      +Text description
      +Boolean is_done
    }

    class TaskModel_Inherited {
      +Date deadline
      +Selection priority
      +_check_deadline()
    }

    TaskModel_Base <|-- TaskModel_Inherited : _inherit (mismo _name)

    Aunque en código veas sólo una clase, conceptualmente estamos extendiendo la clase original con nuevos campos y lógica; siguen siendo el mismo modelo en la BD.

    Herencia por prototipo basada en task_app.task_model

    Queremos crear un nuevo modelo que reutilice la estructura de task_app.task_model, pero guardado en otra tabla y con su propio espacio.

    Ejemplo: modelo task_app.archived_task

    # task_app_extension/models/archived_task.py
from odoo import fields, models

class ArchivedTask(models.Model):
    _name = "task_app.archived_task"
    _inherit = "task_app.task_model"   # prototipo
    _description = "Archived Task"

    archived_date = fields.Datetime(string="Archived On")
    archived_reason = fields.Text(string="Reason")

    📌 Consecuencias: - La tabla task_app_task_model (original) sigue existiendo. - Se crea una nueva tabla task_app_archived_task con: - Campos heredados de task_app.task_model - + archived_date, archived_reason

    Visual — Diagrama de tablas (prototipo)

    erDiagram
    TASK_APP_TASK_MODEL {
      integer id PK
      varchar name
      text description
      boolean is_done
    }

    TASK_APP_ARCHIVED_TASK {
      integer id PK
      varchar name
      text description
      boolean is_done
      timestamp archived_date
      text archived_reason
    }

    Este tipo de herencia se usa cuando quieres una variante del modelo original, con su propia tabla e historias separadas.

    Herencia por delegación con _inherits y task_app

    En este caso, la nueva clase no copia campos, sino que delegamos parte del contenido en otro modelo mediante una relación Many2one obligatoria.

    Ejemplo: task_app.task_extra que delega en task_app.task_model

    # task_app_extension/models/task_extra.py
from odoo import fields, models

class TaskExtra(models.Model):
    _name = "task_app.task_extra"
    _description = "Task Extra Info"
    _inherits = {"task_app.task_model": "task_id"}

    task_id = fields.Many2one(
        "task_app.task_model",
        string="Task",
        required=True,
        ondelete="cascade",
    )

    extra_notes = fields.Text(string="Extra Notes")
    reference_code = fields.Char(string="Reference Code")

    📌 Consecuencias: - Tabla task_app_task_extra tendrá: - id, task_id, extra_notes, reference_code, … - Tabla task_app_task_model se mantiene igual. - Desde task_app.task_extra accedemos a los campos de task_app.task_model como si fueran propios.

    Visual — Delegación

    erDiagram
    TASK_APP_TASK_MODEL {
      integer id PK
      varchar name
      text description
      boolean is_done
    }

    TASK_APP_TASK_EXTRA {
      integer id PK
      integer task_id FK
      text extra_notes
      varchar reference_code
    }

    TASK_APP_TASK_MODEL ||--o{ TASK_APP_TASK_EXTRA : "inherits via task_id"

    Se usa _inherits cuando quieres componer un nuevo modelo a partir de otros, manteniendo tablas separadas pero expuestas como un solo recurso en Odoo.

    Herencia en VISTAS con task_app

    Supongamos que ya tenemos una vista formulario básica para task_app.task_model:

    <record id="view_task_form" model="ir.ui.view">
  <field name="name">task_app.task_model.form</field>
  <field name="model">task_app.task_model</field>
  <field name="arch" type="xml">
    <form string="Task">
      <sheet>
        <group>
          <field name="name"/>
          <field name="description"/>
          <field name="is_done"/>
        </group>
      </sheet>
    </form>
  </field>
</record>

    Ahora veremos cómo heredar esta vista para modificarla.

    Añadir un campo nuevo al formulario (herencia de vista)

    Queremos añadir el campo deadline (añadido por herencia de modelo) justo después de name.

    <record id="view_task_form_inherit_deadline" model="ir.ui.view">
  <field name="name">task_app.task_model.form.inherit.deadline</field>
  <field name="model">task_app.task_model</field>
  <field name="inherit_id" ref="task_app.view_task_form"/>
  <field name="arch" type="xml">
    <field name="name" position="after">
      <field name="deadline"/>
    </field>
  </field>
</record>

    Visual — Vista base vs vista heredada

    flowchart LR
  A[Vista base: Task Form] --> B[Vista heredada: añade Deadline]
  B --> C[Vista final: Name + Deadline + Description + Is Done]

    Modificar atributos de un campo con position="attributes"

    Queremos hacer obligatorio category_id (campo relacional añadido en otra extensión).

    <record id="view_task_form_inherit_category_required" model="ir.ui.view">
  <field name="name">task_app.task_model.form.inherit.category_required</field>
  <field name="model">task_app.task_model</field>
  <field name="inherit_id" ref="task_app.view_task_form"/>
  <field name="arch" type="xml">
    <field name="category_id" position="attributes">
      <attribute name="required">1</attribute>
    </field>
  </field>
</record>

    Insertar pestaña nueva con xpath

    Añadimos una pestaña de información extra sobre la tarea, aprovechando que hemos definido el modelo heredado task_app.task_extra.

    <record id="view_task_form_inherit_extra_tab" model="ir.ui.view">
  <field name="name">task_app.task_model.form.inherit.extra_tab</field>
  <field name="model">task_app.task_model</field>
  <field name="inherit_id" ref="task_app.view_task_form"/>
  <field name="arch" type="xml">
    <xpath expr="//notebook" position="inside">
      <page string="Extra Info">
        <group>
          <field name="reference_code"/>
          <field name="extra_notes"/>
        </group>
      </page>
    </xpath>
  </field>
</record>

    En la práctica, esto requiere que los campos (reference_code, extra_notes) estén disponibles en el modelo (por herencia, related, etc.).

    Herencia en CONTROLADORES (métodos de task_app)

    Herencia en el controlador = sobrescribir métodos en el modelo heredado.

    Ejemplo: sobreescribir create() de task_app.task_model

    Queremos que cada vez que se cree una tarea: - Si no se indica priority, se ponga a Normal. - Marcar una bandera interna.

    from odoo import api, fields, models

class TaskModel(models.Model):
    _inherit = "task_app.task_model"

    internal_flag = fields.Boolean(string="Internal Flag")

    @api.model
    def create(self, vals):
        if not vals.get("priority"):
            vals["priority"] = "1"  # Normal

        record = super().create(vals)
        record.internal_flag = True
        return record

    Visual — Flujo de llamada con super()

    sequenceDiagram
    participant User
    participant TaskModel_Inherit as TaskModel (heredado)
    participant TaskModel_Base as TaskModel (base)

    User->>TaskModel_Inherit: create(vals)
    TaskModel_Inherit->>TaskModel_Base: super().create(vals)
    TaskModel_Base-->>TaskModel_Inherit: record
    TaskModel_Inherit->>TaskModel_Inherit: record.internal_flag = True
    TaskModel_Inherit-->>User: record
