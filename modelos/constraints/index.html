    Constraints en Odoo

    En Odoo, para garantizar la integridad de los datos podemos usar dos tipos de restricciones en los modelos:
    1. SQL constraints (_sql_constraints) → validadas directamente en PostgreSQL.
    2. Python constraints (@api.constrains) → validadas mediante lógica en Python antes de guardar.

    Referencia oficial: Model constraints en Odoo 18

    1) _sql_constraints (SQL Constraints)

    Las restricciones SQL se definen en el atributo de clase _sql_constraints y se aplican directamente en la base de datos PostgreSQL.
    - Se ejecutan a nivel SQL: no dependen de la lógica Python.
    - Son muy rápidas y garantizan consistencia global de los datos.
    - Se expresan como una lista de tuplas con la forma:

    _sql_constraints = [
    ("nombre_constraint", "SQL_EXPRESSION", "Mensaje de error"),
]

    Ejemplo: evitar tareas con el mismo nombre si están activas

    # task_app/models/task_model.py
from odoo import fields, models

class TaskModel(models.Model):
    _name = "task_app.task_model"
    _description = "Task"

    name = fields.Char(string="Name", required=True, index=True)
    active = fields.Boolean(default=True)

    _sql_constraints = [
        (
            "task_app_task_name_uniq",         # identificador único de la constraint
            "UNIQUE (name, active)",           # condición SQL en la tabla
            "It cannot be two tasks with the same name!!",  # mensaje mostrado al usuario
        ),
    ]
    • Aquí se impide que dos tareas activas tengan el mismo name.
    • El error se lanza directamente desde PostgreSQL cuando se intenta insertar o actualizar un registro que viola la condición.
    • Ventaja: imposible saltársela incluso desde procesos externos (importaciones, scripts, etc.).

    2) @api.constrains (Python Constraints)

    Las restricciones Python se definen como métodos en el modelo decorados con @api.constrains.
    - Reciben como parámetro el nombre de los campos a vigilar.
    - La validación se ejecuta cuando alguno de esos campos cambia.
    - Si no se cumple la condición, debe lanzarse una ValidationError.

    Ejemplo: nombre de la tarea con longitud mínima

    # task_app/models/task_model.py
from odoo import api, fields, models
from odoo.exceptions import ValidationError

class TaskModel(models.Model):
    _name = "task_app.task_model"
    _description = "Task"

    name = fields.Char(string="Name", required=True, index=True)

    @api.constrains("name")
    def _check_longitud(self):
        for rec in self:
            if rec.name and len(rec.name) < 5:
                raise ValidationError("The name of the task must have at least 5 characters!")
    • Cada vez que se cambie el campo name, se ejecuta _check_longitud.
    • Si el nombre tiene menos de 5 caracteres, lanza un ValidationError.
    • La transacción se cancela y se muestra el mensaje al usuario.

    3) Comparación rápida

    Aspecto _sql_constraints @api.constrains
    Nivel Base de datos (PostgreSQL) Lógica Python (ORM Odoo)
    Rendimiento Muy alto (ejecutado en SQL) Menor (ejecutado en servidor)
    Flexibilidad Limitado a expresiones SQL (UNIQUE, CHECK, etc.) Total, se puede usar cualquier código Python
    Error Postgres lanza excepción SQL Se lanza ValidationError
    Uso típico Unicidad, valores no nulos, validaciones sencillas Validaciones de negocio más complejas

    4) Buenas prácticas

    • Usa _sql_constraints siempre que sea posible para integridad fuerte en BD.
    • Usa @api.constrains cuando la regla dependa de lógica de negocio compleja que no puede expresarse en SQL.
    • Puedes combinar ambas: por ejemplo, SQL para unicidad y Python para condiciones adicionales.
    • Los mensajes de error deben ser claros para el usuario final.
