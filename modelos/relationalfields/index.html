    Campos relacionales

    En esta sección veremos los campos relacionales del ORM de Odoo.

    Referencia oficial (Odoo 18, campos relacionales)

    Código de ejemplo

    1) Resumen de campos relacionales

    • Many2one: relación N→1. En la BD se materializa como una FK (columna <nombre>_id).
      Parámetros comunes relevantes:

      • comodel_name: modelo destino (ej. "res.users").
      • string: etiqueta en la UI.
      • required: si es obligatorio.
      • index: crea índice en la columna FK.
      • ondelete: comportamiento al borrar el registro destino ("set null", "restrict", "cascade"…).
      • domain: filtra opciones del desplegable (UI/ORM).
      • context: contexto por defecto al abrir la vista/relación.
      • delegate: (avanzado) delegación de campos del comodel.
      • auto_join: puede optimizar búsquedas con JOIN automático.

    • One2many: relación 1→N. No crea columna en el modelo actual; depende de un campo Many2one en el modelo hijo.
      Parámetros clave:

      • comodel_name: modelo hijo.
      • inverse_name: nombre del campo Many2one en el hijo que apunta al padre.
      • domain, context: igual que arriba.
      • ondelete: sólo se usa en vistas/comportamientos específicos, no borra físicamente hijos por sí mismo (el borrado en cascada depende de ondelete del Many2one inverso en el hijo).

    • Many2many: relación N↔N. Se materializa con una tabla relacional.
      Parámetros clave:

      • comodel_name: modelo relacionado.
      • relation (opcional): nombre de la tabla relacional (si no se indica, Odoo genera uno).
      • column1 / column2 (opcionales): nombres de las columnas FK en la tabla relacional (si se omiten, Odoo los genera).
      • string, domain, context: como arriba.
      • ondelete: comportamiento al borrar (por defecto elimina las filas de la tabla relacional; no borra el otro lado).

    Nota: domain y context se aplican tanto en servidor como en cliente para filtrar/parametrizar la interacción. ondelete en Many2one es el que realmente define la política al borrar el destino (SET NULL / RESTRICT / CASCADE).

    2) Modelos de ejemplo

    2.1) task_app.task_model (añadimos category_id y un Many2many tag_ids)

    # task_app/models/task_model.py
from odoo import fields, models

class TaskModel(models.Model):
    _name = "task_app.task_model"
    _description = "Task (basic model)"

    name = fields.Char(string="Name", required=True, index=True)
    description = fields.Text(string="Description")
    is_done = fields.Boolean(string="Done", default=False)

    # --- Relación Many2one: N tareas -> 1 categoría ---
    category_id = fields.Many2one(
        comodel_name="task_app.category_model",
        string="Category",
        ondelete="set null",   # Si se borra la categoría, la tarea queda sin categoría
        index=True
    )

    2.2) task_app.category_model (Many2one hacia Task y One2many inverso)

    A la vez, añadimos un One2many (task_ids) inverso a category_id para cubrir el patrón habitual de categorías→tareas. Puedes quedarte con uno u otro según tu diseño de datos.

    # task_app/models/category_model.py
from odoo import fields, models

class TaskCategory(models.Model):
    _name = "task_app.category_model"
    _description = "Category Model"

    name = fields.Char(string="Name", required=True, index=True)
    active = fields.Boolean(string="Active", default=True)

    # One2many inverso de Task.category_id (patrón clásico: 1 categoría -> N tareas)
    task_ids = fields.One2many(
        comodel_name="task_app.task_model",
        inverse_name="category_id",
        string="Tasks in this Category",
    )

    Diseño de datos: Lo más habitual es usar (2) One2many/Many2one entre Categoría y Tarea: cada Tarea apunta a una Categoría (category_id), y desde Categoría vemos sus tareas con task_ids.

    3) Comentarios sobre parámetros (según documentación)

    Many2one

    • comodel_name (obligatorio): modelo destino (string), p. ej. "task_app.category_model".
    • string: etiqueta visible en la interfaz.
    • ondelete: comportamiento al borrar el destino:
    • "set null": deja el campo a NULL (recomendado en la mayoría de FK opcionales).
    • "restrict": impide borrar si hay registros que apuntan al destino.
    • "cascade": borra también los registros dependientes (usar con extremo cuidado).
    • required, index, help, default: comportamiento estándar.
    • domain, context: filtrar/parametrizar selección (UI/ORM).
    • delegate: delega campos del comodel en este registro (composición).
    • auto_join: puede optimizar búsquedas con JOIN.

    One2many

    • comodel_name (obligatorio): modelo hijo.
    • inverse_name (obligatorio): nombre del Many2one en el hijo que referencia al padre.
    • domain, context, help: igual filosofía.
    • Importante: One2many no crea columna en la tabla; depende del Many2one del hijo. El borrado en cascada se controla en el Many2one del hijo con ondelete.

    Many2many

    • comodel_name (obligatorio).
    • relation: nombre de la tabla relacional (si no se pone, Odoo genera uno).
    • column1 / column2: nombres de las columnas FK en esa tabla (opcional).
    • domain, context, help.
    • Borrado: al eliminar un lado, se eliminan las filas de la tabla relacional, no el otro registro.

    4) Buenas prácticas rápidas

    • Usa ondelete="set null" en Many2one por defecto, y restrict cuando no tenga sentido dejar huérfanos.
    • Añade index=True a Many2one usados en filtros habituales (mejora rendimiento).
    • Prefiere el patrón Category 1→N Tasks (One2many/Many2one) en lugar de enlazar categoría→tarea con otro Many2one a menos que tu caso lo requiera.
    • En Many2many, nombra relation/column1/column2 si quieres control y claridad del esquema.
